## Раздел 7. Контрольные вопросы

### 1. Чем Vite отличается от Create React App?

Главное отличие — что происходит при запуске dev-сервера.

**CRA** собирает webpack'ом весь проект целиком **до** того, как отдаст первую страницу. Чем больше файлов, тем дольше старт и тем медленнее пересборка после правки.

**Vite** в режиме разработки не собирает приложение вообще. Он отдаёт браузеру нативные ES-модули и трансформирует только тот файл, который браузер прямо сейчас запросил. Зависимости из `node_modules` предварительно обрабатываются через esbuild (написан на Go, работает в десятки раз быстрее JS-сборщиков). Отсюда старт за сотни миллисекунд независимо от размера проекта — в нашем случае `ready in 375 ms`.

Для продакшена (`npm run build`) Vite всё-таки собирает бандл — через Rollup, с минификацией и code-splitting.

Дополнительно: HMR (горячая замена модулей) в Vite обновляет только изменённый модуль, а не пересобирает граф, поэтому правка CSS видна мгновенно. И ещё: CRA официально объявлен устаревшим, документация React больше не рекомендует его для новых проектов.

### 2. Что такое CSS-модуль и зачем он нужен? Как обратиться к классу в JSX?

Обычный CSS глобален: класс `.card`, объявленный в одном файле, применится ко всем элементам с этим классом во всём приложении. В большом проекте это приводит к конфликтам имён — два разработчика пишут `.title`, и стили ломают друг друга.

**CSS-модуль** — это файл с именем вида `Имя.module.css`. Сборщик (Vite из коробки) при импорте такого файла превращает каждое имя класса в уникальную строку вроде `_card_1a2b3_4` и возвращает объект соответствий `{ card: "_card_1a2b3_4" }`. Стили становятся локальными для компонента: коллизия невозможна, даже если в десяти компонентах есть свой `.card`.

Обращение в JSX — через импортированный объект:

```jsx
import styles from './ArticleCard.module.css'

<article className={styles.card}>
```

`styles.card` — обычное обращение к свойству объекта. Если класс назван через дефис (`.card-footer`), точечная запись не сработает — нужны скобки: `styles['card-footer']`. Поэтому в проекте классы названы в camelCase.

### 3. Какие семантические теги HTML5 использованы в проекте и почему?

| Тег | Где | Зачем |
|---|---|---|
| `<header>` | `Header.jsx` | Шапка сайта — вводная часть страницы |
| `<nav>` | `Nav.jsx` | Блок навигационных ссылок; скринридер даёт перейти к нему одной командой |
| `<main>` | `App.jsx` | Основное содержимое, уникальное для страницы. На странице должен быть один |
| `<section>` | `ArticleList.jsx` | Тематически связанная группа — список статей |
| `<article>` | `ArticleCard.jsx` | Самодостаточный фрагмент, осмысленный отдельно от страницы. Карточка статьи — ровно такой случай |
| `<footer>` | `ArticleCard.jsx` | Служебная информация блока — автор и дата |
| `<h1>` / `<h2>` | Шапка и карточки | Иерархия заголовков, по которой строится оглавление страницы |
| `<time>` | `ArticleCard.jsx` | Дата в машиночитаемом виде |

Зачем вообще: те же самые блоки можно собрать из `<div>`, и выглядеть будет одинаково. Разница в трёх вещах — **доступность** (скринридеры ориентируются по ориентирам-landmarks, а не по внешнему виду), **SEO** (поисковик понимает, где основной контент, а где навигация) и **читаемость кода** (`<article>` сразу говорит, что внутри, в отличие от `<div className="card">`).

### 4. Как работает `flex-wrap` и `flex: 1 1 calc(...)` при построении сетки?

По умолчанию flex-контейнер держит все элементы в одну строку и сжимает их, сколько бы их ни было. `flex-wrap: wrap` это отменяет: когда элементы перестают помещаться, лишние переносятся на новую строку. Без него сетки не получится — будет один ряд из восьми сплющенных карточек.

`flex: 1 1 calc(...)` — сокращение для трёх свойств:

- `flex-grow: 1` — разрешить расти и делить свободное место поровну;
- `flex-shrink: 1` — разрешить сжиматься, если не помещается;
- `flex-basis: calc(...)` — желаемая ширина до растягивания и сжатия.

Формула `calc((100% - 72px) / 4)` считает ширину одной колонки: из полной ширины вычитаются промежутки (`gap: 24px` между 4 колонками встречается 3 раза = 72px), остаток делится на 4.

Важная деталь из нашего кода: `flex-grow: 1` заставил бы единственную карточку в последнем ряду растянуться на всю ширину — восьмая карточка выглядела бы баннером. Поэтому рядом стоит `max-width` с той же формулой: расти разрешено, но не шире одной колонки.

Адаптивность сделана медиазапросами, которые меняют только делитель и вычитаемое: 4 → 3 → 2 → 1.

### 5. Как данные из `articles.js` попадают в карточки? Опишите путь данных.

```
articles.js  →  ArticleList  →  ArticleCard  →  JSX
```

1. **`src/data/articles.js`** экспортирует массив объектов: `export const articles = [...]`.

2. **`ArticleList.jsx`** импортирует его: `import { articles } from '../../data/articles'`. Это обычный импорт JS-модуля, React тут ни при чём.

3. Внутри JSX вызывается `articles.map(...)`. Метод возвращает новый массив — уже не из объектов, а из элементов React. Массив, вставленный в JSX, React рендерит поэлементно:

   ```jsx
   {articles.map((article) => (
     <ArticleCard key={article.id} article={article} />
   ))}
   ```

4. Запись `article={article}` передаёт объект статьи как **проп** с именем `article`.

5. **`ArticleCard.jsx`** получает все пропы одним объектом и сразу разбирает его в сигнатуре: `function ArticleCard({ article })`. Дальше поля подставляются в разметку — `{article.title}`, `{article.image}`, `{article.author}`.

Ключевое свойство: поток **односторонний, сверху вниз**. Карточка не может изменить `article` — пропы доступны только для чтения. Чтобы изменить данные, правят источник (`articles.js`), и React перерисовывает всё, что от него зависит. Именно поэтому добавление 7-й и 8-й статьи не потребовало правок в компонентах.

### 6. Зачем нужен `key` при рендере списка через `.map()`?

При повторном рендере React сравнивает новое дерево элементов со старым и применяет к DOM минимальный набор изменений. Чтобы сравнить два списка, ему нужно понять, какой элемент нового списка соответствует какому элементу старого. `key` — это и есть идентификатор, по которому устанавливается соответствие.

Без `key` React сопоставляет элементы по позиции в массиве. Пока список статичен, это работает. Но если вставить статью в начало, по позициям сместится всё: React решит, что изменился текст каждой карточки, и перезапишет восемь узлов вместо вставки одного. Хуже того, внутреннее состояние компонентов (раскрытый текст, введённое в поле значение) останется привязанным к позиции и «переедет» на чужую карточку.

С `key={article.id}` React видит, что карточка с `id: 3` — та же самая, просто сдвинулась, и переиспользует существующий DOM-узел вместе с его состоянием.

Требования к ключу: **уникальный среди соседей** (глобальная уникальность не нужна) и **стабильный между рендерами**. Поэтому `id` из данных подходит, а индекс массива (`.map((a, i) => ... key={i})`) — плохой выбор при вставках, удалениях и сортировке: он описывает позицию, а не элемент. `Math.random()` непригоден вовсе — новый ключ на каждом рендере заставляет React удалять и создавать узлы заново.
